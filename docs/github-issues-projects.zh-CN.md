# GitHub Issues 与 Projects 工作流

本章定义人类与 AI 代理使用 GitHub Issues 和 GitHub Projects 管理开发工作的通用方法，适用于单仓库、拆分为多个仓库的产品，以及包含多个产品的项目组合。

关键词 **MUST（必须）**、**MUST NOT（不得）**、**SHOULD（应该）**、**SHOULD NOT（不应该）** 和 **MAY（可以）** 具有规范效力。团队可以调整名称和可选字段，但必须保留本文规定的语义与控制边界。

## 1. 单一记录系统

- Issue 是工作的权威记录，包含问题、范围、验收标准、决策、依赖与完成证据。
- Project 是基于 Issue 的计划视图；其中的字段描述流程与计划，但不能取代 Issue。
- Pull Request 是实施与评审证据。它必须关联 Issue，但不得成为记录范围或验收标准的唯一位置。
- 信息必须只有一个权威位置。不得在标签、Issue 正文和 Project 字段中维护相互竞争的状态、优先级或迭代值。

在仓库策略允许时，修正错字等微小、非实质性维护可以不创建 Issue。实质性实施、行为变更、缺陷、迁移以及已计划的文档工作，必须在开始前建立 Issue。

## 2. 仓库归属

Issue 应创建在主要交付物所属的仓库：

- API、持久化与服务行为归属服务仓库。
- 平台专属体验归属相应客户端仓库。
- 共享契约或库归属其源仓库。
- 全产品协调工作归属组织指定的计划仓库（如有）。

代理在创建 Issue 前必须搜索已有 Issue。不得仅为了让工作出现在另一个看板上而创建重复追踪 Issue；应将现有 Issue 加入相应 Project。

## 3. 跨仓库工作

使用一个父 Issue 表达整体结果，并为每个独立归属的仓库交付物创建一个子 Issue：

```text
父功能
├── service-api：契约与持久化
├── web-client：浏览器体验
├── ios-client：iOS 体验
└── android-client：Android 体验
```

父 Issue 记录共享验收标准、顺序与整体状态。每个子 Issue 记录仓库专属范围、负责人、估算和 Pull Request。依赖必须以 `blocked by` / `blocking` 明确表达，不能只在正文中暗示。在所有必需子 Issue 完成或由获授权人员明确移出范围前，父 Issue 不得标记为 Done。

## 4. 结构化字段

需要筛选、排序、分组、制图或自动化的值，优先使用 Project 字段。推荐字段如下：

| 字段 | 用途 | 指引 |
| --- | --- | --- |
| Status | 当前流程状态 | 只能有一个值；参见下方生命周期。 |
| Priority | 相对业务紧迫度 | 使用较小的等级，如 P0–P3；它不是估算。 |
| Size / Estimate | 交付工作量或复杂度 | 使用统一量表；无法合理估算的工作应拆分。 |
| Iteration | 近期交付窗口 | 只分配给已承诺工作；Backlog 通常不设迭代。 |
| Area | 稳定的产品或技术归属 | 使用少量且持续维护的词汇。 |
| Target date | 真实的外部或运营截止日期 | 不得当作愿望日期；原因应记录在 Issue 中。 |

标签用于仓库自身的分类，如 `bug`、`security` 或 `dependencies`，不得用标签重复 Project 字段。只有发布版本或具有外部意义的结果需要仓库级分组时才使用里程碑。

## 5. Backlog 与看板生命周期

推荐的基础流程是：

```text
Backlog -> Ready -> In Progress -> In Review -> Done
```

团队可以重命名状态，但每个状态必须保留明确含义：

| 状态 | 进入条件 | 退出条件 |
| --- | --- | --- |
| Backlog | 工作值得保留，但尚未承诺。 | 满足 Definition of Ready 并被选中。 |
| Ready | 工作可执行、已排优先级且无阻塞。 | 负责人开始工作。 |
| In Progress | 一名明确负责人正在实施。 | 可评审的 Pull Request 已打开，或附带原因退回 Ready/Backlog。 |
| In Review | 实施正在等待评审、检查或验收。 | 所需评审、检查与验收均完成。 |
| Done | 满足 Definition of Done。 | 仅在完成证据错误或已验收范围发生回归时重新打开。 |

Status 描述当前事实，不得用于表达优先级、团队、发布版本或 Issue 类型。负责人必须在事实变化时更新状态，而不是等到报告周期结束。

## 6. Definition of Ready

Issue 只有满足以下条件才可以进入 Ready：

- 期望结果及其对用户或系统的影响清晰；
- 验收标准可观察、可测试；
- 仓库归属与明确负责人已知；
- 依赖和待决阻塞已识别；
- 在适用时已考虑安全、隐私、迁移、发布与文档影响；
- 工作规模足以在团队正常交付周期内完成，否则已经拆分；
- Priority 已由获授权人员设定；
- Issue 对范围或意图不存在未解决的矛盾。

代理不得把描述不足的 Backlog 条目视为已获授权的工作。代理可以完善 Issue、提出验收标准或请求决策，但不得擅自发明产品行为。

## 7. Definition of Done

Issue 只有满足以下条件才可以进入 Done：

- 所有验收标准均已满足；
- 所需代码、测试、文档、迁移和发布保障均已完成；
- 所需检查与评审均已通过；
- Pull Request 已合并，或仓库规定的等价流程已完成；
- 相关子 Issue 与依赖均已解决；
- 后续工作已经完成，或已记录为关联 Issue；
- Issue 包含足够证据，使其他人可以验证完成情况。

仅关闭 Pull Request、发布构建或在本地完成代码并不足够。工作若取消或被取代，应以对应原因关闭，不得将其呈现为已经交付。

## 8. 在制品限制

当开始工作比完成工作更难时，流程会更顺畅。每个人或代理通常应该同时只负责一个活动实施 Issue。团队应该为 In Progress 和 In Review 设置明确的 WIP 限制。

达到限制后，贡献者应该先评审、测试、解除阻塞或拆分现有工作，再开始新的 Ready 条目。被阻塞的工作仍应保留其真实状态，并必须记录阻塞项、责任方和下次检查点。可以使用独立的 `Blocked` 字段或标记；禁止仅为了隐藏被阻塞的 WIP 而将条目移回 Backlog。

团队应该每日检查滞留在 In Review 的条目，并定义本地响应目标。该目标是服务预期，不是绕过必要评审的许可。

## 9. 迭代与计划节奏

Iteration 是承诺窗口，不是整个 Backlog 的容器。团队应该采用稳定节奏——一到两周是常见起点——并让未承诺工作保持无 Iteration。

迭代计划时：

1. 确认容量和当前 WIP；
2. 按 Priority 顺序只选择 Ready 条目；
3. 验证依赖与归属；
4. 分配 Iteration；
5. 记录明确的交付风险。

未完成工作不得未经评审自动滚入下一迭代；应重新确认范围、优先级、估算和负责人。Backlog 梳理应该移除重复与过时工作、拆分过大的 Issue，并只准备合理数量的近期 Ready 工作。回顾应该使用流程数据改进系统，而不是评价个人。

## 10. 自动化

自动化应该减少事务性工作，但不能掩盖决策。实用的基础自动化包括：

- 将获批准仓库中新建或符合条件的开放 Issue 加入 Project；
- 将新加入条目的 Status 设为 Backlog；
- 关联实施开始时将 Issue 移至 In Progress；
- 关联 Pull Request 可评审时将 Issue 移至 In Review；
- 只有 Issue 按本地完成策略真正关闭时才移至 Done；
- 从活动视图归档旧的 Done 条目，但不删除记录。

除非获授权策略已经提供决策，否则自动化不得分配 Priority、Iteration、Target date、验收标准或产品范围。每个自动转换都应该可逆且可审计。团队必须定期检查工作流失败与仓库过滤器，尤其是在仓库新增、重命名、转移或归档后。

## 11. 代理权限边界

AI 代理可以执行反映已观察事实的事务性更新：将 Issue 加入 Project、将自己设为负责人、关联 Pull Request、更新 Status、记录证据，以及声明或清除已经验证的阻塞。

未经明确授权，代理不得：

- 修改 Priority、Iteration、Target date、范围或验收标准，从而形成新的产品或交付承诺；
- 从父 Issue 中移除必需工作；
- 在满足 Definition of Done 前将工作标记为 Done；
- 为改善看板指标而关闭未解决的 Issue；
- 将沉默、任务指派或自动字段值推断为批准。

当字段与 Issue 或当前仓库事实冲突时，代理必须保留证据、指出矛盾并请求人工决策；可以提出具体解决方案。

## 12. 代理操作检查清单

### 开始之前

- 搜索权威 Issue；仅在不存在时创建。
- 确认仓库归属与跨仓库结构。
- 验证 Definition of Ready、依赖、Priority 与权限。
- 只有工作真正开始时才分配负责人并移至 In Progress。

### 工作期间

- 在 Issue 中维护范围与验收决策。
- 立即记录阻塞与依赖。
- 关联实施证据，并保持 Status 真实。
- 创建关联的后续 Issue，不得把额外范围隐藏在 Pull Request 中。

### 评审之前

- 按仓库现有 Pull Request 标准打开或更新关联 Pull Request。
- 确认测试、检查、文档、迁移和发布要求。
- 只有工作真正可评审时才移至 In Review。

### 完成之前

- 验证每项验收标准和完整的 Definition of Done。
- 确认所需子 Issue 与依赖均已完成。
- 在 Issue 中加入简明的完成证据。
- 只有满足仓库的合并与关闭策略后才移至 Done。

## 13. 推荐视图与检查节奏

一个 Project 可以提供多个视图而不重复 Issue：

- **Backlog：** 按优先级排序、按 Area 分组并排除 Done。
- **Ready queue：** 只显示 Ready，按 Priority 与条目年龄排序。
- **Delivery board：** 显示 Ready 至 In Review，并按 Status 分组。
- **Current iteration：** 过滤为当前 Iteration，并按 Status 分组。
- **Review queue：** 显示 In Review，最旧的排在最前。
- **Roadmap：** 只显示有实际意义的 Iteration 或 Target date 的工作。

每日检查交付看板，定期梳理 Backlog，在迭代边界制定计划，并周期性审计过时 Issue、字段词汇、自动化和 WIP 限制。Project 的健康标准是让交付事实更容易看见，而不是填满每一个字段。
